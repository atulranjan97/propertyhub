---How Next Auth works---
1. Serverless function for authentication: (So we use a serverless function for authentication. Next auth uses API routes often implemented as serverless functions to handle authentication related operations like signing in, signing out and session management, so we'll be creating API routes but we're basically passing it off to next auth)
2. Create a session: (so when a user logs in, next auth creates a session for that user and the session contains information like user's identity and authentication state, and the session is signed with a secret key to ensure its integrity and prevent tampering)
3. Store the session: (It store the session so the session data is stored in a cookie on the client side. That cookie is then sent with each request to the server)
4. Verifying the session: (and then Verifying the session so on subsequent request the server checks the cookie to verify the session, and it does this by validating the session signature using a secret key. And if the signature is valid and the data is intact, then the server processes the request as authenticated)
5. Accessing Protect Routes: (and then finally accessing protected routes so the client send the cookie with every request and we get access to any routes that are protected.)
Next auth uses middleware or API routes to use that session data from the cookie to determine if the user is authorized to access that requested resource. So, for example, we're gonna have a page where we can create a property and that's gonna be a protected route, you're not gonna be able to go to that page if you're not logged in

There're ton of providers mentioned below:
Google, Facebook, Twitter, Github, Discord, Slack, Dropbox, Auth0, Netlify, Okta, Reddit, Salesforce, Todoist, Spotify, Twitch, Zoom
So, Oauth is an open standard for access delegation and this is what allows a user to grant a third-party website or application to access their information without sharing their actual credentials, so we can't see you actual Google passoword or fb password or anything like that, which makes it very secure, so it's secure by default.

---Secure By Default---
- Promotes the use of passwordless sign-in mechanisms, you password is not shared, its not known. 
- Its design to be secured by default and encourages the best practices for safegaurding user data 
- It uses cross-site request forgery tokens on POST routes (sign in, sign out)
- There is a Default cookie policy aims for the most restrictive policy appropriate for each cookie
- When JSON web token are enabled, they are encrypted by default
- Auto generate symmetric signin and encryption keys for developer convenience
- It features tab window syncing and keep alive messages to support short lived sessions
- It attempts to Implement the latest guidance published by the open web application security project. 
So using something like next-auth with a provider is more secure than trying to implement the authentication youself. It's a complete solution thats been tested  and its used by many developers and big companies
And these days, there's very few cases where developers create a completely custom authentication solution over using something like next-auth. Not only is it more secure, but it's much easier to implement

                                                                  ---Server Actions---
They allow us to run server side functions in our next app. And we already have used server components which are components that render on the server. But server actions are functions that run on the server and we can essentially do anything we want with them. We can also submit forms directly to an action using the action attribute. So instead of using an onClick handler like we would with client sides
Now actions can also be run within a client component. So they're very flexible and they can be used in different ways. And you also aren't limited to actions with forms. They can be invoked from form event handlers, even within a useEffect hook.  
Now we briefly went over API routes and they're a vital part of Next.js, You can use them to execute server side code, It would be a good idea if you need your API routes to be exposed for other projects, but if you're building a single app like we are then actions are much more efficient and easier way to go, and we can run these function directly in our next app, we don't need to worry about setting up API routes and making extra HTTP requests

A server Actions can be defined with the React 'use server' directive. You can place the directive at the top of an async function to mark the function as a server action

Traditional MERN stack (MongoDB, Express, React, Node) me flow kaafi clear aur layered hota tha. Frontend (React) aur backend (Express/Node) completely alag hote the. Jab user form submit karta tha—maan lo “add property” jaisa case—React se ek HTTP request (usually `fetch` ya `axios`) API endpoint par jaati thi, jaise `/api/properties`. Ye request backend ke Express server tak pahunchti thi, jahan route handler likha hota tha. Wahan validation hoti thi, phir MongoDB me data save hota tha, aur response wapas client ko milta tha. Agar image upload karni hoti thi, to middleware jaise `multer` use hota tha jo file ko stream karke ya disk/cloud me store karta tha. Is approach me separation of concerns clear tha: frontend sirf UI handle karta tha, backend pura business logic aur DB.

Ab Next.js (especially App Router + Server Actions) me ye boundary kaafi blur ho gayi hai. Yahan tum ek hi project me frontend aur backend dono likhte ho. Server Actions ka concept ye hai ki tum directly component ke andar ya ek server file me function likh ke usko form ke `action` me pass kar sakte ho. Jab form submit hota hai, wo function server pe execute hota hai—beech me explicit API route banane ki zarurat nahi padti. Iska matlab ye hua ki jo kaam pehle `fetch → API → controller → DB` ke through hota tha, ab wo directly `form → server function → DB` ho gaya. Code kam ho gaya, flow simple lagta hai, aur chhoti applications ke liye ye kaafi powerful hai.

Lekin internally kya ho raha hai, wo samajhna important hai. Jab tum Server Action use karte ho, Next.js background me ek special request bana ke us server function ko call karta hai—bas tumhe manually API route likhne ki zarurat nahi padti. Ye abstraction developer experience ko better banata hai, lekin iska matlab ye nahi ki HTTP layer gayab ho gayi hai—wo bas hidden ho gayi hai. Isi wajah se jab tum heavy data (jaise images) bhejte ho, to wo pura payload memory me load ho sakta hai, kyunki traditional backend jaisa streaming/middleware handling tum explicitly control nahi kar rahe hote.

Isliye difference ye hai: MERN me tumhara full control hota hai request lifecycle par—tum decide karte ho kaise file handle hogi, kaise stream hogi, kaise memory manage hogi. Next.js Server Actions me convenience zyada hai, lekin control thoda kam ho jata hai, especially large payloads ke case me. Isi wajah se simple form data (text, numbers, small payloads) ke liye Server Actions perfect hain, lekin image upload jaise use cases me traditional API route ya direct cloud upload (jaise Cloudinary) abhi bhi better aur safer approach hai.

-------------------------------------Serialization-------------------------------------------
Jab tum Next.js App Router me **Server Component se Client Component ko data pass karte ho**, tab ek important rule hota hai: data **JSON-serializable** hona chahiye. Ab “JSON-serializable” ka matlab kya hai? Simple words me, aisa data jo `JSON.stringify()` se safely string me convert ho sake aur `JSON.parse()` se wapas same structure me aa jaye. Isme sirf basic types allowed hote hain: **string, number, boolean, null, arrays, aur plain objects** (simple `{}` jisme sirf key-value pairs ho). Lekin MongoDB/Mongoose ka data is rule ko tod deta hai, kyunki wo special types use karta hai jaise `ObjectId` (Mongo ka unique ID type), `Date` objects, aur kabhi-kabhi `Buffer`. Ye objects internally methods rakhte hain (jaise `toJSON`, `toString`, etc.) aur unka structure simple JSON jaisa nahi hota. Isi wajah se Next.js error deta hai: *“Only plain objects can be passed…”*.

Technical level par samjho: Next.js Server Component se Client Component ko data bhejne ke liye us data ko **serialize** karta hai (network ke through bhejne layak format me convert karta hai). Ye process almost `JSON.stringify()` jaisa hota hai. Agar kisi object me custom prototype, methods, ya complex internal structure ho (jaise `new ObjectId()`), to wo proper tarike se serialize nahi hota, aur Next.js usse reject kar deta hai. Isi ko “non-serializable data” bolte hain.

Ab `.lean()` ka role: jab tum Mongoose query me `.lean()` lagate ho, to wo Mongoose document (jo heavy object hota hai with methods like `.save()`, `.populate()`) ko ek **plain JavaScript object** me convert kar deta hai. Lekin important baat: `.lean()` sirf wrapper hataata hai, **data types convert nahi karta**. Isliye `_id` still `ObjectId` hi rehta hai, aur `createdAt` still `Date` object hi rehta hai. Matlab object plain hai, lekin uske andar ke values abhi bhi non-serializable ho sakte hain.

Is problem ka solution hai **serialization step manually karna**. Jab tum `_id.toString()` karte ho, to tum complex `ObjectId` ko simple string me convert kar dete ho. Jab tum `date.toISOString()` use karte ho, to `Date` object ek ISO string (e.g. `"2026-04-09T04:32:58.549Z"`) me convert ho jata hai. Ye dono fully JSON-safe hote hain. Ek shortcut hai `JSON.parse(JSON.stringify(data))`, jo internally sab non-serializable cheezon ko string me convert kar deta hai aur ek clean plain object return karta hai. Is process ko hi “data serialization” bolte hain.

Short me pura concept:
MongoDB → complex data types (ObjectId, Date) → `.lean()` → plain object but still complex values → **serialization (stringify / manual convert)** → fully JSON-safe object → Client Component.
Agar tum ye last step skip kar doge, to Next.js App Router me hamesha ye error aayega.

## Next.js + Leaflet SSR Error — Revision Notes

---

### Problem Kya Thi

Jab project run kiya, browser console mein ek error aaya jiska message tha — *"window is not defined"* aur Next.js automatically server rendering se client rendering pe switch ho gaya. Yahi root problem thi.

---

### Next.js Kaise Kaam Karta Hai — Pehle Ye Samjho

Next.js ek fullstack framework hai jo code **do jagah** chalata hai — pehle server pe, phir browser pe. Jab user koi page open karta hai, toh server pehle poora HTML bana ke browser ko bhejta hai. Isse page jaldi dikhta hai aur SEO bhi better hota hai. Uske baad browser mein JavaScript load hoti hai aur page interactive ho jaata hai. Is poori process ko **Server Side Rendering (SSR)** kehte hain.

---

### Error Kyun Aaya

Leaflet ek map library hai jo **sirf browser mein kaam karti hai**. Woh internally `window` aur `document` jaisi cheezein use karti hai jo sirf browser ke paas hoti hain. Server ek Node.js environment hai — wahan `window` exist hi nahi karta. Toh jab Next.js ne server pe Leaflet ko import kiya, Leaflet ne `window` dhundha, nahi mila, aur crash ho gaya.

---

### `'use client'` Ne Kaam Kyun Nahi Kiya

Yahan sabse important aur confusing concept hai. `'use client'` likhne ke baad bhi error aa raha tha, toh lagta hai ki ye directive kuch kaam nahi karta — lekin aisa nahi hai.

`'use client'` ka sirf itna matlab hai ki **React is component ko client pe render karega**. Lekin Next.js build process ke dauran **server sabhi modules ko import karke check karta hai** — chahe unpe `'use client'` laga ho ya na laga ho. Leaflet usi import step pe crash karti hai, React render hone se pehle hi. Isliye `'use client'` se kuch farak nahi pada.

Ek aasaan analogy — socho `'use client'` ek director hai jo kehta hai "ye scene sirf set pe shoot hoga." Lekin Leaflet toh script padhte waqt hi stage pe aa gayi aur girr gayi — shooting se pehle hi.

---

### Pehla Error — `ssr: false` Server Component Mein

Pehla solution try kiya — `PropertyDetails.jsx` mein `dynamic()` with `ssr: false` use kiya. Lekin ek naya error aaya ki **`ssr: false` sirf Client Components mein allowed hai**, Server Components mein nahi.

`PropertyDetails.jsx` ek Server Component tha kyunki usme `'use client'` nahi likha tha. Next.js mein by default har component Server Component hota hai. `dynamic({ ssr: false })` sirf tab kaam karta hai jab woh component khud Client Component ho.

---

### Final Solution — Wrapper Component

Sabse clean solution tha ek **alag wrapper component** banana — `PropertyMapWrapper.jsx`. Isme teen cheezein ki gayi:

Pehli — file ke upar `'use client'` likha, toh ye poora component Client Component ban gaya. Doosri — isi file mein `dynamic(() => import('./PropertyMap'), { ssr: false })` use kiya. Teesri — `PropertyDetails.jsx` mein `PropertyMap` ki jagah `PropertyMapWrapper` import kiya.

Is approach ka faida ye raha ki `PropertyDetails.jsx` **Server Component hi raha** — sirf map wala chhota sa hissa client pe gaya. Next.js ka proper pattern yehi hai ki jitna ho sake server pe rakho, sirf zaroorat wali cheez client pe bhejo.

---

### `dynamic({ ssr: false })` Asal Mein Kya Karta Hai

Ye Next.js ko instruction hai ki **is module ko server pe bilkul mat chhuo** — isko sirf browser mein load karo jab page ready ho. Jab tak browser mein JavaScript load nahi hoti, wahan ek loading state ya khaali jagah dikhti hai. Jaise hi browser ready hota hai, tab Leaflet load hoti hai, `window` available hota hai, aur map render ho jaata hai.

---

### Ek Line Mein Yaad Rakhne Wali Baat

> `'use client'` React ko batata hai kahan render karna hai. `dynamic({ ssr: false })` Next.js ko batata hai kahan **import** karna hai. Map fix karne ke liye dono cheezein ek saath chahiye thi — isliye wrapper component banana pada.
